# Instrucciones para el copiloto

Estás en un harness de spec-driven development para producto. Antes de trabajar en cualquier tarea:

1. Lee los cinco docs de contexto, cada uno de una naturaleza distinta:
   - `docs/doc_company_context.md` (estable, se precarga: qué es la empresa, productos, negocio, mercado — se rellena por proyecto).
   - `docs/doc_market_research.md` (vivo, con fecha: comparables de mercado, cambia rápido, la skill `live-research` lo refresca).
   - `docs/doc_open_questions.md` (lo que no sabemos: se pregunta al equipo, nunca se inventa).
   - `docs/doc_design_system.md` (identidad visual fijada — paleta, tipografía, layout. **Solo lo leen `establish-design-system`, `build-prototype` en modo alta fidelidad, y `finalize-product-design`**; el resto de skills no lo necesita, no lo precargues para ellas).
   - `docs/doc_voice.md` (voz y copy fijados — reglas Do/Don't, tono por contexto, texto real de piezas bloqueadas. **Solo lo leen `lock-content-voice`, `build-prototype`, y `finalize-product-design`**; el resto no lo precarga).
2. Lee `docs/doc_base_standards.md` (cómo se decide, se especifica, se valida, y se cambia el propio harness aquí).
3. Cada skill tiene un comando real en `.claude/commands/` (`/discovery`, `/monetize`, `/evaluate`, `/business-case`, `/prioritize`, `/spec`, `/validate`, `/human-validate`, `/design-system`, `/voice`, `/prototype`, `/finalize-design`, `/research`): si el problema llega como texto libre, elige la skill correcta por descripción; si llega como comando, ya está resuelto.
   - problema abierto / "entiende qué hacemos" → `/discovery` → `skills/discovery-operator` (paso cero)
   - "¿cómo monetizamos este punto sin romper la experiencia?" → `/monetize` → `skills/design-monetization-model`
   - "¿deberíamos entrar en X?" → `/evaluate` → `skills/evaluate-vertical`
   - "argumenta el caso / build vs integrate" → `/business-case` → `skills/business-case`
   - "hay varias opciones, ¿cuál primero?" → `/prioritize` → `skills/prioritize-roadmap`
   - "define/especifica esto para ingeniería" → `/spec` → `skills/write-spec` (primera pasada: borrador ligero que origina el prototipo y, si aplica, la hipótesis de `validate-fast` — no la versión final, ver la segunda pasada más abajo)
   - "muéstrame cómo se vería un flujo" → `/prototype` → `skills/build-prototype` (por defecto, BAJA fidelidad: gris/neutro, no necesita `/design-system` antes — orden estándar de la industria, verificado vía research 2026-09-17. Reordenado 2026-09-17: corre justo después del spec-borrador, ANTES de `/validate`/`/human-validate` y antes de `/design-system`/`/voice` — auditado contra la práctica real de equipos AI-native en Anthropic, OpenAI, Google y Meta: el prototipo se valida barato y temprano, antes de invertir en validación formal o en pulir marca, no al final. Solo si se pide explícitamente ALTA fidelidad lee `doc_design_system.md`; si no existe todavía, lo dice y sugiere `/design-system`, pero nunca negocia una identidad nueva dentro del prototipo. Un prototipo valida UN flujo rápido — no es el diseño final de todo el producto, eso es `/finalize-design`)
   - "¿cómo lo validamos rápido?" → `/validate` → `skills/validate-fast` (si aplica; ahora corre después del prototipo, así que valida contra el flujo real que ya existe, no solo una hipótesis en papel)
   - "¿cómo ejecuto esto con usuarios/operadores reales?" → `/human-validate` → `skills/human-validation` (el cómo, después de que validate-fast elige el método; si el proyecto es solo/sin usuarios externos que validar, una revisión directa del propio PM puede cumplir este rol — informal, no una de las 13 skills, pero sigue siendo el chequeo real antes de invertir en identidad/voz)
   - "quiero explorar/fijar paleta, tipografía o el look visual, para una versión de alta fidelidad" → `/design-system` → `skills/establish-design-system` (se fija una vez, no se repite cada sesión — ver nota abajo; corre después de que el flujo de baja fidelidad ya pasó por validación)
   - "esto no suena como yo / hace falta fijar la voz o el copy real" → `/voice` → `skills/lock-content-voice` (se fija una vez, mismo trato que `/design-system` pero para palabras — ver nota abajo; mismo momento que `/design-system`)
   - "hace falta el diseño completo y definitivo de cada pantalla/estado, listo para ingeniería" → `/finalize-design` → `skills/finalize-product-design` (viene DESPUÉS de que el flujo ya se validó, la identidad ya está fijada, y la voz/copy ya está fijada — verificado vía research 2026-09-17, señal MEDIA-FUERTE: un prototipo de alta fidelidad y un diseño final completo son entregables distintos incluso dentro del mismo rol de diseño, no lo mismo con otro nombre)
   - "el diseño ya está finalizado, hace falta cerrar el spec antes de pasarlo a ingeniería" → `/spec` → `skills/write-spec` (segunda pasada, sobre el mismo borrador: ahora se revisa y se cierra con lo que realmente quedó validado y finalizado, no con lo que se esperaba al principio. Esto es lo que `/plan` toma como artefacto durable)
   - "falta un dato de mercado, búscalo ahora" → `/research` → `skills/live-research` (contexto vivo; datos internos van a `doc_open_questions.md`, no aquí)

Además, `/plan` toma un spec ya escrito y produce el plan de implementación bajo el agente `engineer`, no el PM.

Flujo completo del PM (reordenado 2026-09-17 tras auditar la práctica real de equipos de producto AI-native en Anthropic, OpenAI, Google y Meta — el prototipo se mueve temprano, no al final): descubrir → elegir modelo → evaluar vertical → argumentar el caso → priorizar → especificar (borrador ligero: la decisión convertida en algo que origina el prototipo) → prototipar (baja fidelidad, valida UN flujo barato y rápido) → validar qué / validar cómo (si aplica — ahora contra el prototipo real, no una hipótesis en papel; en un proyecto solo sin usuarios externos, una revisión directa del PM puede cumplir este rol) → establecer identidad visual y voz (`establish-design-system` + `lock-content-voice`, solo si hace falta alta fidelidad, después de que el flujo ya se validó) → finalizar el diseño completo (`finalize-product-design`, solo cuando haga falta el inventario completo de pantallas) → especificar de nuevo (segunda pasada de `write-spec`: cierra el spec con lo que quedó realmente validado y finalizado, no con lo que se esperaba al principio — esto es lo que `/plan` toma como artefacto durable). `establish-design-system` y `lock-content-voice` no son pasos que se repitan cada sesión: cada uno se fija una vez (cuando se necesita alta fidelidad por primera vez), y solo se revisitan con una revisión deliberada — no reabras ninguno solo porque un prototipo "no se siente diferenciado" o "no suena como yo"; eso se resuelve volviendo a `/design-system` o `/voice`, no iterando dentro de `/prototype`. `finalize-product-design` tampoco se repite por sesión: se corre cuando el inventario de pantallas está listo para pasar a ingeniería, no como sustituto de validar un flujo. `live-research` tampoco es un paso fijo del flujo, pero por la razón opuesta: se invoca ad hoc cada vez que falta un dato de mercado durante cualquiera de los otros pasos. No todo problema usa todas las skills; elige según cuál sea.

Adopta el rol de `ai-specs/.agents/product-manager.md` por defecto.

Regla dura: el spec (formato EARS) es el artefacto que se entrega a ingeniería. El PM es dueño del problema y los criterios; ingeniería es dueña del plan y las tasks. No mezcles los dos roles.

Importante: el modelo de monetización actual de la empresa (lo que sea que `docs/doc_company_context.md` describa) es el modelo BASE, no una restricción sobre los modelos nuevos que este harness te pida evaluar.

Esta copia del harness no trae ejemplos resueltos — son específicos de cada proyecto/empresa. Cada `SKILL.md` describe su propio formato de salida esperado.
