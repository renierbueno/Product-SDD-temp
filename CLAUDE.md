# Instructions for the copilot

You are in a spec-driven development harness for product. Before working on any task:

1. Read the five context docs, each of a different nature:
   - `docs/doc_company_context.md` (stable, preloaded: what the company is, products, business, market — filled in per project).
   - `docs/doc_market_research.md` (live, dated: market comparables, changes fast, the `live-research` skill refreshes it).
   - `docs/doc_open_questions.md` (what we don't know: asked of the team, never invented).
   - `docs/doc_design_system.md` (fixed visual identity — palette, typography, layout. **Only read by `establish-design-system`, `build-prototype` in high-fidelity mode, and `finalize-product-design`**; the rest of the skills don't need it, don't preload it for them).
   - `docs/doc_voice.md` (fixed voice and copy — Do/Don't rules, tone by context, real text of locked pieces. **Only read by `lock-content-voice`, `build-prototype`, and `finalize-product-design`**; the rest don't preload it).
2. Read `docs/doc_base_standards.md` (how the harness itself decides, specifies, validates, and changes here).
3. Each skill has a real command in `.claude/commands/` (`/discovery`, `/monetize`, `/evaluate`, `/business-case`, `/prioritize`, `/spec`, `/validate`, `/human-validate`, `/design-system`, `/voice`, `/prototype`, `/finalize-design`, `/research`): if the problem arrives as free text, pick the right skill by description; if it arrives as a command, it's already resolved.
   - open problem / "understand what we do" → `/discovery` → `skills/discovery-operator` (step zero)
   - "how do we monetize this shared touchpoint without breaking the experience?" → `/monetize` → `skills/design-monetization-model`
   - "should we enter X?" → `/evaluate` → `skills/evaluate-vertical`
   - "make the case / build vs integrate" → `/business-case` → `skills/business-case`
   - "there are several options, which one first?" → `/prioritize` → `skills/prioritize-roadmap`
   - "define/specify this for engineering" → `/spec` → `skills/write-spec` (first pass: a light draft that originates the prototype and, if applicable, the hypothesis for `validate-fast` — not the final version, see the second pass below)
   - "show me what a flow would look like" → `/prototype` → `skills/build-prototype` (LOW fidelity by default: gray/neutral, doesn't need `/design-system` first — standard industry order, verified via research 2026-09-17. Reordered 2026-09-17: runs right after the spec draft, BEFORE `/validate`/`/human-validate` and before `/design-system`/`/voice` — audited against the real practice of AI-native teams at Anthropic, OpenAI, Google, and Meta: the prototype gets validated cheaply and early, before investing in formal validation or polishing the brand, not at the end. Only reads `doc_design_system.md` if HIGH fidelity is explicitly requested; if it doesn't exist yet, it says so and suggests `/design-system`, but never negotiates a new identity inside the prototype. A prototype validates ONE fast flow — it's not the final design of the whole product, that's `/finalize-design`)
   - "how do we validate this fast?" → `/validate` → `skills/validate-fast` (if applicable; now runs after the prototype, so it validates against the real flow that already exists, not just a hypothesis on paper)
   - "how do I run this with real users/operators?" → `/human-validate` → `skills/human-validation` (the how, after validate-fast picks the method; if the project is solo/has no external users to validate with, a direct review by the PM themselves can fill this role — informal, not one of the 13 skills, but still the real check before investing in identity/voice)
   - "I want to explore/lock the palette, typography, or visual look, for a high-fidelity version" → `/design-system` → `skills/establish-design-system` (locked once, not repeated every session — see note below; runs after the low-fidelity flow has already passed validation)
   - "this doesn't sound like me / we need to lock the voice or the real copy" → `/voice` → `skills/lock-content-voice` (locked once, same treatment as `/design-system` but for words — see note below; same moment as `/design-system`)
   - "we need the complete, final design of every screen/state, ready for engineering" → `/finalize-design` → `skills/finalize-product-design` (comes AFTER the flow is already validated, the identity is already locked, and the voice/copy is already locked — verified via research 2026-09-17, MEDIUM-STRONG signal: a high-fidelity prototype and a complete final design are distinct deliverables even within the same design role, not the same thing under a different name)
   - "the design is already finalized, we need to close the spec before handing it to engineering" → `/spec` → `skills/write-spec` (second pass, over the same draft: now it gets reviewed and closed with what actually got validated and finalized, not with what was expected at the start. This is what `/plan` takes as the durable artifact)
   - "we're missing a market data point, look it up now" → `/research` → `skills/live-research` (live context; internal data goes to `doc_open_questions.md`, not here)

Also, `/plan` takes an already-written spec and produces the implementation plan under the `engineer` agent, not the PM.

Full PM flow (reordered 2026-09-17 after auditing the real practice of AI-native product teams at Anthropic, OpenAI, Google, and Meta — the prototype moves early, not at the end): discover → pick a model → evaluate vertical → make the case → prioritize → specify (light draft: the decision turned into something that originates the prototype) → prototype (low fidelity, validates ONE cheap and fast flow) → validate what / validate how (if applicable — now against the real prototype, not a hypothesis on paper; on a solo project with no external users, a direct review by the PM can fill this role) → establish visual identity and voice (`establish-design-system` + `lock-content-voice`, only if high fidelity is needed, after the flow is already validated) → finalize the complete design (`finalize-product-design`, only when the full screen inventory is needed) → specify again (second pass of `write-spec`: closes the spec with what actually got validated and finalized, not what was expected at the start — this is what `/plan` takes as the durable artifact). `establish-design-system` and `lock-content-voice` are not steps that repeat every session: each is locked once (when high fidelity is needed for the first time), and only revisited with a deliberate review — don't reopen either just because a prototype "doesn't feel differentiated" or "doesn't sound like me"; that's solved by going back to `/design-system` or `/voice`, not by iterating inside `/prototype`. `finalize-product-design` also doesn't repeat per session: it runs when the screen inventory is ready to hand off to engineering, not as a substitute for validating a flow. `live-research` isn't a fixed step in the flow either, but for the opposite reason: it's invoked ad hoc whenever a market data point is missing during any of the other steps. Not every problem uses every skill; pick based on which one it is.

Adopt the role in `ai-specs/.agents/product-manager.md` by default.

Hard rule: the spec (EARS format) is the artifact handed off to engineering. The PM owns the problem and the criteria; engineering owns the plan and the tasks. Don't mix the two roles.

Important: the company's current monetization model (whatever `docs/doc_company_context.md` describes) is the BASE model, not a restriction on the new models this harness asks you to evaluate.

This copy of the harness doesn't ship with solved examples — those are specific to each project/company. Each `SKILL.md` describes its own expected output format.
